# Forensic Imaging Methodology

## What Is a Forensic Image?

A forensic image is a complete, bit-for-bit copy of a storage device or partition — including allocated files, deleted files, slack space, and unallocated space. Unlike a standard file copy, a forensic image captures the entire volume at the sector level, meaning nothing is omitted or altered.

This is critical in incident response because investigators must never work directly on original evidence. Doing so risks modifying timestamps, overwriting deleted data, or inadvertently tainting the evidence chain.

---

## Why RAW Format?

This lab used the **RAW image format (.img)**, also known as a "dd image." RAW is the most widely supported forensic format — it is simply a sector-by-sector binary copy with no proprietary container. It can be read by virtually any forensic tool (Autopsy, Volatility, FTK, The Sleuth Kit, etc.).

Other common formats include E01 (EnCase Evidence File), which supports compression and encryption, and AFF (Advanced Forensic Format). RAW was chosen here for simplicity and maximum compatibility.

## Hash Verification & Evidence Integrity

### Why Two Hashes?

OSForensics computed two hashes simultaneously during acquisition:

| Hash | Algorithm | Purpose |
|------|-----------|---------|
| Primary | SHA-256 | Strong cryptographic integrity verification |
| Secondary | MD5 | Legacy compatibility; widely used in legal proceedings |

SHA-256 is considered cryptographically strong — a collision (two different files producing the same hash) is computationally infeasible with current technology. MD5 is technically deprecated for security use due to known collision vulnerabilities, but remains widely accepted in forensic and legal contexts as a secondary check.

### Acquisition Hashes (this lab)

```
Primary Hash (SHA-256): cfa10a826b02b1cc793b271070db07fbaaf8fbc7168d66206075361b2589cf09
Secondary Hash (MD5):   16b018f502cd9e4ad681b3833063c52d
```

These values are recorded in the case log and in the `.img.info.txt` metadata file generated by OSForensics. To verify integrity at any future point, a forensic examiner re-hashes the image file and compares against these values. A match confirms the image has not been altered since acquisition.

## Direct Sector Copy Method

OSForensics used **Direct Sector Copy** — the imaging engine reads each sector of the source partition sequentially and writes it to the output file, bypassing the operating system's file system layer. This captures:

- Active files and directories
- Deleted files (sectors not yet overwritten)
- File system metadata (MFT records, directory entries)
- Slack space (unused space at the end of allocated clusters)
- Unallocated space

This is why forensic images are larger than the "used space" shown in Windows Explorer — they capture everything on the volume, not just visible files.

---

## Write Blocking

In professional forensic investigations, a **hardware write blocker** is inserted between the evidence drive and the forensic workstation. This device intercepts any write commands at the hardware level, ensuring the source drive cannot be modified during imaging.

In this lab, the equivalent was achieved through:

1. **OSForensics "Disable Shadow Copy" setting** — prevented Windows VSS from creating shadow copies during imaging, which could have modified the source
2. **OSFMount read-only mounting** — the forensic image was mounted in read-only mode, preventing any modification to the copy during analysis

The mounted image (G:) had no "New Folder" option in the right-click context menu — direct confirmation of read-only enforcement.

## Chain of Custody

Chain of custody documents every person who handled the evidence, every action taken, and every location the evidence occupied. In OSForensics, this is managed through:

- **Case creation with logging enabled** — every action is timestamped in the case log
- **Case metadata** — Case Name, Investigator, Organization, Contact Details, Timezone
- **Acquisition metadata** — stored in the `.img.info.txt` file alongside the image
- **The Manage Case interface** — provides tabs for Chain of Custody, Description of Evidence, and Offense & Custody Data

In a real investigation, this case file would be exported and preserved as part of the evidence package.

## Forensic Image vs. File Copy

| Property | File Copy (xcopy/robocopy) | Forensic Image |
|----------|---------------------------|----------------|
| Copies active files | ✅ | ✅ |
| Copies deleted files | ❌ | ✅ |
| Copies file system metadata | ❌ | ✅ |
| Copies slack space | ❌ | ✅ |
| Preserves timestamps | Partial | ✅ |
| Hash verification | ❌ | ✅ |
| Read-only mountable | ❌ | ✅ |
| Admissible as evidence | Rarely | Yes (if properly documented) |

## Tools Used in This Lab

### OSForensics (PassMark Software)
A commercial digital forensics platform offering case management, disk imaging, file system browsing, hash verification, deleted file recovery, registry analysis, and more. Version 10 was used in this lab (Trial Edition).

### PassMark OSFMount
A free utility from PassMark that mounts forensic image files as virtual drives in Windows. Supports RAW, E01, AFF, and other formats. Enforces read-only access to protect the image during analysis.

## Relevant Industry Standards

**NIST SP 800-86** — Guide to Integrating Forensic Techniques into Incident Response. Covers the forensic process: collection, examination, analysis, and reporting.

**RFC 3227** — Guidelines for Evidence Collection and Archiving. Defines best practices for handling digital evidence, including maintaining integrity and chain of custody.

**ISO/IEC 27037** — Guidelines for identification, collection, acquisition, and preservation of digital evidence.

## Applicability to SOC & Incident Response Roles

This skill set maps directly to real-world IR workflows:

- **Tier 2/3 SOC Analysts** are often responsible for evidence collection when escalating to a forensic team or law enforcement
- **IR responders** must image endpoints before re-imaging or returning systems to service
- **Understanding forensic soundness** helps analysts know what evidence is available, what analysis is possible, and how to articulate findings in incident reports
- **Hash verification** is a transferable skill — the same principle applies when verifying file integrity in malware analysis, log integrity in SIEM pipelines, and software supply chain security
